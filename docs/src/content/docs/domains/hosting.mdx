A domain is hosted from a line of the platform's config. Domain teams write the domain's code and
never write CDK. The platform provides everything the code runs with and behind.

The config, its checks and the stacks are in `infra/app`, with a
[stack](/flex-platform/infrastructure/overview/#stacks) for every domain account and every domain.
The constructs and the names they use are in `domains/infra` (`@repo/domain-infra`).

## Declaring a domain

Each domain account in an environment lists the domains it hosts in that environment, each by its
name, or as `{ name, disabled: true }` when it is [disabled](#disabling-a-domain):

```ts
domainAccounts: [
  {
    name: "domain00",
    account: "098640806149",
    domains: [
      "domain-a",
      { name: "domain-b", disabled: true },
    ],
    zone: {
      name: "development.flex-platform.once.service.gov.uk",
      id: "Z0835542Q6J8ILWJ1RGR",
    },
    network: { availabilityZones: ["eu-west-2a", "eu-west-2b"] },
    gateways: [],
  },
],
```

The Frontdoor routes `/app/<name>/...` to a domain, and its resources are named from its name.
Config holds no routes, and nothing else about what the domain does. See
[routing a request](#routing-a-request).

A domain is hosted only in the environments that list it. Moving it to another domain account is
moving its name to that account's list.

The stage lists the domain too, once, in its own `domains`, whichever of its environments host
it. The entry names the GitHub repository that may [release](#releasing-a-domains-function) the
domain, by GitHub's IDs for the repository and its owner, or `null` until the repository exists:

```ts
domains: [
  {
    name: "domain-a",
    repository: { name: "example-org/domain-a", id: "700000001", ownerId: "800000001" },
  },
  { name: "domain-b", repository: null },
],
```

`gh api repos/<owner>/<repository> --jq '.id, .owner.id'` prints the two IDs.

<Aside type="caution" title="Moving a domain between accounts">
Moving a domain's name does not move its function or code. The destination account gets a new
domain stack, and the domain team must release the function there before it can serve requests.
The previous account's domain stack and its resources must be removed separately.
</Aside>

### Disabling a domain

List a domain as `{ name, disabled: true }` to stop routing to it. Its stack stays as it is, with
its API, its host, its log groups and its name, which no other account in the environment may
take. The Frontdoor's routes leave it out, so a request for it, once its token is verified, gets
the 404 an unknown domain gets, and never reaches its API. Listing it by its name again restores
the route and recreates nothing. Release the function the route will reach before enabling it.

Disabling withdraws the route and nothing else: it doesn't stop an invocation already running, or
change what the function's role may do. The routes change when the Frontdoor's stack deploys, and
copies of Lambda@Edge can route to the domain until the new version has replaced them.

Removing a domain from config is different. Its stack leaves the app, and CDK doesn't delete a
stack the app no longer builds, so it is deleted by hand. Its log groups are retained, so adding
the domain back later fails until they are imported into its new stack or deleted.

### Checks

Before building any stage, the app checks every domain, disabled ones included:

- its name is 1 to 32 lowercase letters, digits and hyphens, starting with a letter and not
  ending with a hyphen;
- its name is used once in its environment, across all of the environment's domain accounts,
  since the Frontdoor routes by name alone;
- it is in its stage's `domains`, once, and every domain there is hosted in at least one of the
  stage's environments;
- it is hosted in the environment its own environment's `release` promotes from, if it promotes;
- its execution role's name, `domain-<environment>-<name>-execution`, is within IAM's 64
  characters. It is the longest of the names Lambda and IAM limit, so the others fit too. Each name
  is within 32 alone, but the two together can pass it: together they may be 46 at most.

## What a domain account provides

`DomainAccountStack`, `domainaccount-<environment>-<account>`, holds what every domain in a domain
account shares in one environment. Nothing in it names a domain, so adding or removing one never
changes it. It is in eu-west-2, the region the edge signs requests for, and has termination
protection: deleting it would take the domains' certificate with it, and leave the account's API
Gateway logging setting naming a deleted role.

| Construct | Builds |
|---|---|
| `WildcardCertificate` | A CAA record at the zone's apex, `0 issue "amazon.com"`, so only Amazon may issue certificates for the zone. Then `*.<zone>`, validated through DNS in the account's own zone. |
| `ApiGatewayLogging` | API Gateway's logging role, set on the account, so every API in it can write its access and execution logs |

One wildcard certificate serves every domain because ACM limits a certificate's first name to 64
characters. A certificate for `<domain>.<zone>` would leave a domain's name as few as 18.

ACM generates the certificate's ARN, so the stack writes it to SSM, at
`/flex/domain/<environment>/certificate-arn`, where each domain's stack reads it when it deploys. If
the certificate is ever replaced, each domain's stack deploys with `--force` to read the new ARN,
and CloudFormation can't delete the old certificate while a domain's custom domain still uses it.

API Gateway's logging role has AWS's managed policy, `AmazonAPIGatewayPushToCloudWatchLogs`, so it
may create, write to and read any log group in the account and region. API Gateway refuses a
logging role with less: it checks the role's effective permissions, so it refuses one scoped to the
domains' log groups, or one denied `logs:CreateLogGroup`. Every API's log groups are created by its
own stack instead, before its stage, so API Gateway never creates one.

## What a domain provides

`DomainStack`, `domain-<environment>-<domain>`, holds one domain's API and the host it answers at,
and the log group and roles its function runs and is released with, in the domain account that
hosts it, in eu-west-2. It holds no function: the API reaches the domain's function by name. It has
no termination protection, since everything in it but its log groups, which are retained, is built
again from config. CDK doesn't delete a stack the app no longer builds, so a domain removed from
config keeps its stack until someone deletes it.

| Construct | Builds |
|---|---|
| `ProxyApi` | `domain-<environment>-<domain>-api`, a regional REST API whose `execute-api` address is turned off, with its resource policy, its `ANY` methods, its stage, `default`, its access and execution log groups, the role it invokes the function through, its gateway responses, and its [refusal alarms](#watching-refusals) |
| `ApiHost` | `<domain>.<zone>`, with the domain account's wildcard certificate, mapped to the stage at its root, and its alias record in the account's zone |
| `PlatformLogGroup` | `/flex/domain/<environment>/<domain>/function`, the log group the domain's function logs to |
| `ExecutionRole` | `domain-<environment>-<domain>-execution`, the role the domain's function runs as, and its permission boundary. See [permissions](#permissions). |
| `DeployRole` | `domain-<environment>-<domain>-deploy`, the role a release assumes to create and update the domain's function. See [permissions](#permissions). |

The stage is traced with X-Ray, logs errors, and never logs request or response bodies. Its access
logs go to `/flex/domain/<environment>/<domain>/api-access`, one JSON line per request. Its
execution logs go to `API-Gateway-Execution-Logs_<api id>/default`, which the stack creates before
the stage, so it is encrypted and kept for a year, and API Gateway never creates it first. The stage has no
throttling of its own, so it shares the account's limits.

### Network

Every domain runs in its domain account's [network](/flex-platform/infrastructure/network/), in
the isolated subnets, with no route to the internet. There is no setting to change this: a domain
reaches an upstream through a gateway, and a gateway that needs the internet has its own
[placement](/flex-platform/reference/glossary/#placement). The network creates the `domain`
security group a domain's function runs in, which may reach only the `lambda` endpoint: see
[what a workload may reach](/flex-platform/infrastructure/network/#what-a-workload-may-reach).

The stack reads two of the network's
[parameters](/flex-platform/infrastructure/network/#ids-other-stacks-read) when it deploys, and
holds the deploy role to them. The deploy role may read them too, so a release places a function
from the same values:

| Parameter | Holds |
|---|---|
| `/flex/network/<environment>/isolated-subnet-ids` | The isolated subnets' IDs |
| `/flex/network/<environment>/security-group/domain` | The `domain` security group's ID |

If the network is ever replaced, the stack deploys with `--force` to read the new IDs.

### Permissions

Each domain's function runs as a role of its own, `domain-<environment>-<domain>-execution`. It
may:

- invoke any function named `gateway-<environment>-*`, with any qualifier, such as `:live`. Any
  domain may call any gateway in its environment, and only gateways have that name. The stack
  takes the pattern from `gatewayFunctionPattern` in `gateways/infra`;
- write to its own domain's log group, `/flex/domain/<environment>/<domain>/function`, and use
  its stack's key for that through CloudWatch Logs;
- send its traces to X-Ray;
- create and remove the network interfaces Lambda needs to run it in the VPC.

Lambda manages those network interfaces with the role's credentials, which the function's code
holds too. So the role denies the network interface actions to any call made from a domain's code,
which Lambda marks with the function's ARN. Lambda's own calls carry no function's ARN, so they
are still allowed.

No domain's role may write to another's log group, so the log group a line is in shows which
domain wrote it. A stream's name doesn't: Lambda names each stream, but a domain's code can write
a stream under any name.

The role runs code that teams outside the platform write, with that code holding its credentials.
So it has a permission boundary that holds the same statements. Whatever policy is ever attached to
the role, by mistake or by hand, a domain's code can do no more than the boundary allows. The deploy
role has none: it runs no one's code, and its denies already hold whatever else it is ever allowed.

Each domain has a deploy role too, `domain-<environment>-<domain>-deploy`. It may be assumed only
by principals in its own account that are themselves allowed to assume it. It may create,
configure, release and read only its domain's function, with the function's versions and aliases,
read the two network parameters above, describe the network Lambda checks a function's placement
against, and pass only its domain's
execution role, only to Lambda. So no release can give a function another domain's role, and with
it another domain's log group. It denies:

- every Lambda action on any function named `gateway-<environment>-*`;
- creating or configuring a domain's function with no VPC, in any subnet but the isolated ones, or
  with any security group but the `domain` group.

The denies hold whatever else the role is ever allowed, so a domain's function can only run where
the platform places it.

### Who can call it

Every method uses IAM authorisation, and synth fails for any API Gateway method in the app without
it: see [checks](/flex-platform/infrastructure/overview/#checks). The Frontdoor signs each request
with SigV4 as its edge role. The resource policy allows the Frontdoor's account only when the
caller is that role, and denies everyone else, so a principal in the domain account with
permission to invoke APIs is refused too.

The policy names the role in a condition, never as a principal, because API Gateway refuses a
policy that names a role that doesn't exist yet.

### Watching refusals

Each API counts IAM authorisation's refusals from its access log's `errorResponseType`, in the
namespace `flex/domain/<environment>/<domain>/api`, and alarms when they are sustained:

| Metric | Counts | Alarm | Goes off at |
|---|---|---|---|
| `bypass-attempts` | `MISSING_AUTHENTICATION_TOKEN` and `ACCESS_DENIED`: a request sent unsigned, or signed by anyone but the edge role | `domain-<environment>-<domain>-api-bypass-attempts` | 10 or more in each of three five-minute periods in a row |
| `signing-faults` | `INVALID_SIGNATURE` and `EXPIRED_TOKEN`: a signature that doesn't verify | `domain-<environment>-<domain>-api-signing-faults` | 1 or more in each of three five-minute periods in a row |

The host is in a public zone, so scanners find it, and the bypass alarm is set above that
background. A fault in the edge's signing refuses every request the edge sends, so any sustained
count of signing faults is one.

The metrics divide refusals by type, not by who sent them. A direct caller can send a signature
that doesn't verify, which counts as a signing fault, and the edge role refused by a mistake in
the resource policy counts as a bypass attempt. The alarms have no action until the platform has
alerting, so they notify no one: someone has to look at them.

### Investigating an origin refusal alarm

1. In Logs Insights, query `/flex/domain/<environment>/<domain>/api-access` for the alarm's
   `errorResponseType` values in its period. Note when they started and how many there were.
2. For signing faults, check whether requests through the Frontdoor are failing too: the
   Frontdoor answers them with `x-rejected-by: api-gateway`, and
   `/flex/frontdoor/<environment>/origin-request`, in the frontdoor account in eu-west-2, logs
   `origin_request_forwarded` for them at the same time. If so, the edge's signing is broken. Look
   for a recent change to the edge function, its role or this API, and roll it back. If Frontdoor
   traffic is being served, the signatures are someone else's: treat them as bypass attempts.
3. For bypass attempts, check first whether requests through the Frontdoor are refused too: a 403
   `auth_error` with `x-rejected-by: api-gateway`, while the edge logs `origin_request_forwarded`.
   If so, the API's resource policy no longer allows the edge role: check the domain's stack for
   drift, and deploy it again. Otherwise, judge the volume and pattern. A scanner's requests are
   few and spread out. A sustained stream of requests, signed especially, is a security incident.
   Escalate it with the log lines as evidence.

### Errors

When API Gateway refuses a request itself, it answers in the same shape as the Frontdoor, with
`x-rejected-by: api-gateway`, as the Frontdoor's own refusals name the part that refused:

| Response | Status | Body |
|---|---|---|
| Unauthorised, access denied, invalid signature, missing authentication token, expired token | 401 or 403 | `{"message":"Unauthorized","type":"auth_error"}` |
| Throttled | 429 | `{"message":"Too many requests","type":"client_error"}` |
| Any other 4xx | 4xx | `{"message":<API Gateway's own message>,"type":"client_error"}`. Its messages are fixed, so no caller's text reaches the body. |
| Any 5xx | 5xx | `{"message":"Internal server error","type":"server_error"}` |

A response from the domain's own code passes through unchanged.

### TLS

The custom domain uses `SecurityPolicy_TLS13_1_2_PFS_PQ_2025_09` in `STRICT` mode. It offers
TLS 1.3 and still accepts TLS 1.2 with forward secrecy. Only CloudFront reaches the host, over
IPv4, so it has one A record.

## Routing a request

The domain's API answers every path and method under the domain's root, with `ANY` on `/` and on
`/{proxy+}`, and passes each request to the domain's function unchanged. The API checks that the
Frontdoor signed the request, and nothing about the path, method or body. The domain's code decides
which routes exist and how each is handled, and answers anything else itself, such as with a 404.

So a domain adds or changes a route by releasing its code. No change to the platform's config or
stacks is needed.

The API invokes the function's `live` alias, by an ARN built from the function's name, through a
role of its own. Only API Gateway in the domain account may assume the role, and it may invoke only
that domain's `live` alias. So the function needs no resource policy, and a function created again
under the same name needs nothing added. Each release publishes a version and moves `live` to it,
so the API reaches only code that was deliberately released, and moving the alias back rolls a
release back. Until the first release there is no `live`, and the API answers 500.

## The domain's function

The function is named `domain-<environment>-<name>`, built by `domainFunctionName` in
`@repo/domain-infra`. Everything that refers to the function finds it by this name.

## Releasing a domain's function

<Badge text="Planned" variant="caution" />

A domain's code will be uploaded once, and the same upload released to each environment in turn.
Config already says which way code reaches each environment, in its `release`: `"publish"` where
new code enters the stage, or `{ promoteFrom }`, naming the environment whose released code it
takes. In platform-prod, `development` publishes, `staging` promotes from `development`, and
`production` from `staging`. The repository the stage's `domains` names for a domain is the only
one that will be able to release it.

A release will create and update a domain's function as `domain-<environment>-<name>-deploy`. It
will set:

- the name, `domain-<environment>-<name>`;
- the role, `domain-<environment>-<name>-execution`;
- the isolated subnets and the `domain` security group, read from the network's parameters above
  as the deploy role. The deploy role refuses a configuration with no VPC, so a release sends them
  with every configuration update;
- logging to `/flex/domain/<environment>/<name>/function`;
- `FLEX_ENVIRONMENT`, the environment's name, which the code uses only to build names, such as a
  gateway's function name, and never to choose what it does;
- active tracing, so Lambda sends its traces to X-Ray.

Then it will publish a version and point the `live` alias at it. The deploy role can enforce the
function's name, role and network, but not its logging, environment or tracing, which only the
release will set. A release that sets another log group loses the function's logs, since its role
may write to no other.
