A line of the platform's config hosts a domain. Domain teams write the domain's code and never
write CDK. The platform provides everything the code runs with and sits behind.

The config, its checks and the stacks are in `infra/app`. There is a
[stack](/flex-platform/infrastructure/overview/#stacks) for every domain account and every domain.
The constructs, and the names they use, are in `domains/infra` (`@repo/domain-infra`).

## Declaring a domain

Define each domain once, in `infra/app/src/config/domains.ts`. The definition names the GitHub
repository that may [release](/flex-platform/domains/releasing/) the domain. It names it by GitHub's
IDs for the repository and its owner, or by `null` until the repository exists:

```ts title="config/domains.ts"
export const domainA: DomainConfig = {
  name: "domain-a",
  repository: { name: "example-org/domain-a", id: "700000001", ownerId: "800000001" },
};
```

`gh api repos/<owner>/<repository> --jq '.id, .owner.id'` prints the two IDs.

Each domain account in an environment then lists the domains it hosts in that environment. List
each one as defined, or add `disabled: true` to [disable](#disabling-a-domain) it:

```ts
domainAccounts: [
  {
    name: "domain00",
    account: "098640806149",
    domains: [domains.domainA, { ...domains.domainB, disabled: true }],
    zone: {
      name: "development.flex-platform.once.service.gov.uk",
      id: "Z0835542Q6J8ILWJ1RGR",
    },
    network: { availabilityZones: ["eu-west-2a", "eu-west-2b"] },
    gateways: [],
  },
],
```

The Frontdoor routes `/app/<name>/...` to a domain, and the domain's resources are named from its
name. Config holds no routes, and nothing else about what the domain does. See
[routing a request](#routing-a-request).

A domain is hosted only in the environments that list it. To move it to another domain account,
move it to that account's list.

<Aside type="caution" title="Moving a domain between accounts">
Moving a domain does not move its function or code. The destination account gets a new
domain stack, and the domain team must release the function there before it can serve requests.
The previous account's domain stack and its resources must be removed separately.
</Aside>

### Disabling a domain

Add `disabled: true` to a domain's entry to stop routing to it. Its stack stays as it is, with its
API, its host, its log groups and its name. No other account in the environment may take the name.
The Frontdoor's routes leave the domain out. Once a request's token is verified, the Frontdoor
answers it with the same 404 as an unknown domain, and the request never reaches the API. List the
domain as defined again to restore the route. Nothing is recreated. Release the function the route
will reach before you enable it.

Disabling withdraws the route and nothing else. It doesn't stop an invocation that is already
running, or change what the function's role may do. The routes change when the Frontdoor's stack
deploys. Until the new version of Lambda@Edge has replaced every copy, old copies can still route
to the domain.

Removing a domain from config is different. Its stack leaves the app, and CDK doesn't delete a
stack the app no longer builds. So delete the stack by hand, after you turn off its
[termination protection](/flex-platform/infrastructure/overview/#stacks). Its log groups are
retained. If you add the domain back later, the deploy fails until the log groups are imported into
its new stack or deleted.

### Checks

Before it builds any stage, the app checks every domain, including disabled ones:

- Its name is 1 to 32 lowercase letters, digits and hyphens. It starts with a letter and doesn't
  end with a hyphen.
- Its name is used once in its environment, across all of the environment's domain accounts. This
  is because the Frontdoor routes by name alone.
- It has the same repository, or none, wherever its stage hosts it.
- If its environment's `release` promotes from another environment, the domain is hosted in that
  environment too.
- Its execution role's name, `domain-<environment>-<name>-execution`, is within IAM's 64
  characters. This is the longest of the names that Lambda and IAM limit, so the others fit too.
  The environment's name and the domain's name are each within 32 alone, but together they can
  pass the limit. Together they may be 46 at most.

## What a domain account provides

`DomainAccountStack`, `domainaccount-<environment>-<account>`, holds what every domain in a domain
account shares in one environment. Nothing in it names a domain, so adding or removing a domain
never changes it. It is in eu-west-2, the region the edge signs requests for. It has termination
protection, because deleting it would take the domains' certificate with it. It would also leave
the account's API Gateway logging setting naming a deleted role.

| Construct | Builds |
|---|---|
| `WildcardCertificate` | A CAA record at the zone's apex, `0 issue "amazon.com"`, so only Amazon may issue certificates for the zone. Then `*.<zone>`, validated through DNS in the account's own zone. |
| `ApiGatewayLogging` | API Gateway's logging role, set on the account, so every API in it can write its access and execution logs |

One wildcard certificate serves every domain because ACM limits a certificate's first name to 64
characters. A certificate for `<domain>.<zone>` would leave a domain's name as few as 18.

ACM generates the certificate's ARN, so the stack writes it to SSM at
`/flex/domain/<environment>/certificate-arn`. Each domain's stack reads it from there when it
deploys. If the certificate is ever replaced, deploy each domain's stack with `--force` to read the
new ARN. CloudFormation can't delete the old certificate while a domain's custom domain still uses
it.

API Gateway's logging role has AWS's managed policy, `AmazonAPIGatewayPushToCloudWatchLogs`. So it
may create, write to and read any log group in the account and region. API Gateway refuses a
logging role with less, because it checks the role's effective permissions. It refuses a role
scoped to the domains' log groups, and one denied `logs:CreateLogGroup`. Instead, each API's own
stack creates its log groups before its stage, so API Gateway never creates one.

## What a domain provides

`DomainStack`, `domain-<environment>-<domain>`, holds one domain's API and the host the API answers
at. It also holds the log group the domain's function runs with, and the roles it runs and is
released with. The stack is in the domain account that hosts the domain, in eu-west-2. It holds no
function: the API reaches the domain's function by name. A domain
[removed from config](#disabling-a-domain) keeps its stack until someone deletes it.

| Construct | Builds |
|---|---|
| `ProxyApi` | `domain-<environment>-<domain>-api`, a regional REST API whose `execute-api` address is turned off, with its resource policy, its `ANY` methods, its stage, `default`, its access and execution log groups, the role it invokes the function through, its gateway responses, and its [refusal alarms](#watching-refusals) |
| `ApiHost` | `<domain>.<zone>`, with the domain account's wildcard certificate, mapped to the stage at its root, and its alias record in the account's zone |
| `PlatformLogGroup` | `/flex/domain/<environment>/<domain>/function`, the log group the domain's function logs to |
| `ExecutionRole` | `domain-<environment>-<domain>-execution`, the role the domain's function runs as, and its permission boundary. See [permissions](#permissions). |
| `DeployRole` | `domain-<environment>-<domain>-deploy`, the role a release assumes to create and update the domain's function. See [permissions](#permissions). |

The stage is traced with X-Ray and logs errors. It never logs request or response bodies:

- Its access logs go to `/flex/domain/<environment>/<domain>/api-access`, one JSON line per
  request.
- Its execution logs go to `API-Gateway-Execution-Logs_<api id>/default`. The stack creates this
  log group before the stage, so it is encrypted and kept for a year, and API Gateway never creates
  it first.

The stage has no throttling of its own, so it shares the account's limits.

### Network

Every domain runs in the isolated subnets of its domain account's
[network](/flex-platform/infrastructure/network/), with no route to the internet. No setting
changes this. A domain reaches an upstream through a gateway, and a gateway that needs the internet
has its own [placement](/flex-platform/reference/glossary/#placement). The network creates the
`domain` security group that a domain's function runs in. That group may reach only the `lambda`
endpoint. See
[what a workload may reach](/flex-platform/infrastructure/network/#what-a-workload-may-reach).

The stack reads three of the network's
[parameters](/flex-platform/infrastructure/network/#ids-other-stacks-read) when it deploys. It
holds the deploy role to the first two, and the deploy role may read them too, so a release places
a function from the same values. It holds the execution role to the third.

| Parameter | Holds |
|---|---|
| `/flex/network/<environment>/isolated-subnet-ids` | The isolated subnets' IDs |
| `/flex/network/<environment>/security-group/domain` | The `domain` security group's ID |
| `/flex/network/<environment>/endpoint/lambda` | The `lambda` endpoint's ID |

If the network is ever replaced, deploy the stack with `--force` to read the new IDs.

### Permissions

Each domain's function runs as a role of its own, `domain-<environment>-<domain>-execution`. It
may:

- invoke any function named `gateway-<environment>-*`, through its `live` alias and no other way.
  Any domain may call any gateway in its environment, and only gateways have that name. The stack
  takes the pattern from `gatewayAliasPattern` in `gateways/infra`, as the network's
  [`lambda` endpoint](/flex-platform/infrastructure/network/#endpoints) does;
- write to its own domain's log group, `/flex/domain/<environment>/<domain>/function`, and use its
  stack's key for that through CloudWatch Logs;
- send its traces to X-Ray;
- create and remove the network interfaces Lambda needs to run it in the VPC.

It may invoke a gateway only through the network's `lambda` endpoint. A domain's code holds the
role's credentials, and could give them away in a response or a log line. So the role denies
invoking any function any other way, and the credentials invoke nothing from outside the network.

Lambda manages the network interfaces with the role's credentials, which the function's code holds
too. So the role denies the network interface actions to any call made from a domain's code. Lambda
marks such a call with the function's ARN. Lambda's own calls carry no function's ARN, so they are
still allowed.

No domain's role may write to another domain's log group, so the log group a line is in shows which
domain wrote it. A stream's name doesn't show this. Lambda names each stream, but a domain's code
can write a stream under any name.

The role runs code that teams outside the platform write, and that code holds the role's
credentials. So the role has a permission boundary that holds the same statements. Whatever policy
is ever attached to the role, by mistake or by hand, a domain's code can do no more than the
boundary allows. The deploy role has no boundary. It runs no one's code, and its denies already
hold whatever else it is ever allowed.

Each domain has a deploy role too, `domain-<environment>-<domain>-deploy`. Only the stage's release
worker may assume it. The role trusts the stage's shared account, on the condition that the caller
is the worker's role, `shared-release-worker`. The trust names the role by a condition because IAM
refuses a principal that doesn't exist yet. The deploy role may:

- create, configure, release and read only its domain's function, with the function's versions and
  aliases;
- read the two network parameters above;
- describe the network that Lambda checks a function's placement against;
- read its own domain's bundles in the [code bucket](/flex-platform/domains/release-pipeline/#the-code-bucket);
- pass only its domain's execution role, and only to Lambda.

Lambda reads the bundle a function is created or updated from as the caller, so the role must be
able to read it. The bucket lets every deploy role read any bundle, so the role's own policy is
what holds a release to its domain's code. Because the role may pass only its domain's execution
role, no release can give a function another domain's role, and with it another domain's log
group. The role denies:

- every Lambda action on any function named `gateway-<environment>-*`;
- creating or configuring a domain's function with no VPC, in any subnet but the isolated ones, or
  with any security group but the `domain` group.

The denies hold whatever else the role is ever allowed, so a domain's function can only run where
the platform places it.

### Who can call it

Every method uses IAM authorisation. Synth fails for any API Gateway method in the app without it.
See [checks](/flex-platform/infrastructure/checks-and-tests/#checks). The Frontdoor signs each request with
SigV4 as its edge role. The resource policy allows the Frontdoor's account only if the caller is
that role, and denies everyone else. So it refuses even a principal in the domain account that has
permission to invoke APIs.

The policy names the role in a condition, never as a principal, because API Gateway refuses a
policy that names a role that doesn't exist yet.

### Watching refusals

Each API counts the refusals IAM authorisation makes, and alarms when they are sustained. It counts
them from its access log's `errorResponseType`, in the namespace
`flex/domain/<environment>/<domain>/api`:

| Metric | Counts | Alarm | Goes off at |
|---|---|---|---|
| `bypass-attempts` | `MISSING_AUTHENTICATION_TOKEN` and `ACCESS_DENIED`: a request sent unsigned, or signed by anyone but the edge role | `domain-<environment>-<domain>-api-bypass-attempts` | 10 or more in each of three five-minute periods in a row |
| `signing-faults` | `INVALID_SIGNATURE` and `EXPIRED_TOKEN`: a signature that doesn't verify | `domain-<environment>-<domain>-api-signing-faults` | 1 or more in each of three five-minute periods in a row |

The host is in a public zone, so scanners find it. The bypass alarm is set above that background.
A fault in the edge's signing refuses every request the edge sends, so any sustained count of
signing faults is a fault.

The metrics divide refusals by type, not by who sent them. A direct caller can send a signature
that doesn't verify, which counts as a signing fault. If a mistake in the resource policy refuses
the edge role, that counts as a bypass attempt. The alarms have no action until the platform has
alerting, so they notify no one. Someone has to look at them.

### Investigating an origin refusal alarm

1. In Logs Insights, query `/flex/domain/<environment>/<domain>/api-access` for the alarm's
   `errorResponseType` values in its period. Note when they started and how many there were.
2. For signing faults, check whether requests through the Frontdoor are failing too. The Frontdoor
   answers them with `x-rejected-by: api-gateway`. At the same time,
   `/flex/frontdoor/<environment>/origin-request`, in the frontdoor account in eu-west-2, logs
   `origin_request_forwarded` for them. If so, the edge's signing is broken. Look for a recent
   change to the edge function, its role or this API, and roll it back. If the Frontdoor's traffic
   is being served, the signatures are someone else's. Treat them as bypass attempts.
3. For bypass attempts, first check whether requests through the Frontdoor are refused too. They
   get a 403 `auth_error` with `x-rejected-by: api-gateway`, while the edge logs
   `origin_request_forwarded`. If so, the API's resource policy no longer allows the edge role.
   Check the domain's stack for drift, and deploy it again. Otherwise, judge the volume and
   pattern. A scanner's requests are few and spread out. A sustained stream of requests,
   especially signed ones, is a security incident. Escalate it with the log lines as evidence.

### Errors

When API Gateway refuses a request itself, it answers in the same shape as the Frontdoor. It adds
`x-rejected-by: api-gateway`, in the same way that the Frontdoor's own refusals name the part that
refused:

| Response | Status | Body |
|---|---|---|
| Unauthorised, access denied, invalid signature, missing authentication token, expired token | 401 or 403 | `{"message":"Unauthorized","type":"auth_error"}` |
| Throttled | 429 | `{"message":"Too many requests","type":"client_error"}` |
| Any other 4xx | 4xx | `{"message":<API Gateway's own message>,"type":"client_error"}`. Its messages are fixed, so no caller's text reaches the body. |
| Any 5xx | 5xx | `{"message":"Internal server error","type":"server_error"}` |

A response from the domain's own code passes through unchanged.

### TLS

The custom domain uses `SecurityPolicy_TLS13_1_2_PFS_PQ_2025_09` in `STRICT` mode. It offers
TLS 1.3, and still accepts TLS 1.2 with forward secrecy. Only CloudFront reaches the host, over
IPv4, so the host has one A record.

## Routing a request

The domain's API answers every path and method under the domain's root, and passes each request to
the domain's function unchanged. It has `ANY` methods on `/` and on `/{proxy+}`. The API checks that
the Frontdoor signed the request, and nothing about the path, method or body. The domain's code
decides which routes exist and how it handles each. It answers anything else itself, such as with a
404. So a domain adds or changes a route by releasing its code. No change to the platform's config
or stacks is needed.

Two paths at a domain's root never reach it: `/ping` and `/sping`. API Gateway keeps both for its
own health check at the root of a custom domain name. It answers them itself, without checking a
signature or running the domain's code. So the Frontdoor answers `/app/<domain>/ping` and
`/app/<domain>/sping` with its own 404. Give such a route another name, or put it under another
segment, such as `/v1/ping`.

The API invokes the function's `live` alias through a role of its own, by an ARN built from the
function's name. The role has these limits:

- Only API Gateway may assume it.
- Only a principal in the domain account can set it on an API.
- It may invoke only that domain's `live` alias.

The role's trust carries no `aws:SourceAccount` condition. API Gateway sends none when it assumes
an integration's role, so the condition would refuse every request. Because the API invokes through
this role, the function needs no resource policy. A function created again under the same name
needs nothing added.

Each release publishes a function version and moves `live` to it, so the API reaches only code
that was deliberately released. Until the first release there is no `live`, and the API answers
with a 500.

## The domain's function

The function is named `domain-<environment>-<name>`, built by `domainFunctionName` in
`@repo/domain-infra`. Everything that refers to the function finds it by this name.

A release creates the function and sets everything about it. See
[what a release does](/flex-platform/domains/release-pipeline/#what-a-release-does).
