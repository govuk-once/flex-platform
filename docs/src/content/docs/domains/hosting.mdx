title: Hosting a domain

A domain is hosted from a line of the platform's config. Domain teams write the domain's code and
never write CDK. The platform provides everything the code runs with and behind.

The config and its checks are in `infra/app`. The constructs and the names they use are in
`domains/infra` (`@repo/domain-infra`). No stack in the app creates them, so nothing deploys a
domain. Each part of this page that is planned says so.

## Declaring a domain

Each domain account in an environment lists the names of the domains it hosts in that
environment:

```ts
domainAccounts: [
  {
    name: "domain00",
    account: "098640806149",
    domains: ["domain-a", "domain-b"],
    zone: {
      name: "development.flex-platform.once.service.gov.uk",
      id: "Z0835542Q6J8ILWJ1RGR",
    },
  },
],
```

The Frontdoor routes `/app/<name>/...` to a domain, and its resources are named from its name.
Config holds no routes, and nothing else about what the domain does. See
[routing a request](#routing-a-request).

A domain is hosted only in the environments that list it. Moving it to another domain account is
moving its name to that account's list.

### Checks

Before building any stage, the app checks every domain:

- its name is 1 to 32 lowercase letters, digits and hyphens, starting with a letter and not
  ending with a hyphen;
- its name is used once in its environment, across all of the environment's domain accounts,
  since the Frontdoor routes by name alone;
- its function's name, `domain-<environment>-<name>`, is within Lambda's 64 characters. Each name
  is within 32 alone, but the two together can pass it.

## What a domain account provides

`DomainAccount` builds what every domain in a domain account shares in one environment. Nothing in
it names a domain: the roles reach the domains' resources by name pattern, so adding or removing a
domain never changes it. It is built in eu-west-2, the region the edge signs requests for.

| Resource | Does |
|---|---|
| CAA record | At the zone's apex, `0 issue "amazon.com"`: only Amazon may issue certificates for the zone |
| Wildcard certificate | `*.<zone>`, validated through DNS in the account's own zone, after the CAA record. Each domain's custom domain uses it. |
| `/flex/domain/<environment>/certificate-arn` | An SSM parameter holding the certificate's ARN, which ACM generates. Each domain's stack reads it. |
| Domain security group | The security group every domain's function is placed in. See [network](#network). |
| `/flex/domain/<environment>/security-group-id` | An SSM parameter holding the security group's ID, for whatever creates the domains' functions |
| `/flex/domain/<environment>/function` | The log group every domain's function logs to |
| `domain-<environment>-execution` | The role every domain's function runs as. See [permissions](#permissions). |
| `domain-<environment>-integration` | The role every domain's API invokes its function through |
| API Gateway's logging role | Set on the account, so every API in it can write its access and execution logs |

One wildcard certificate serves every domain because ACM limits a certificate's first name to 64
characters. A certificate for `<domain>.<zone>` would leave a domain's name as few as 18.

### Network

Every domain runs in the VPC's isolated subnets, with no route to the internet. There is no
setting to change this: a domain reaches an upstream through a gateway, and a gateway that needs
the internet has its own [placement](/flex-platform/reference/glossary/#placement).

The VPC isn't the platform's, so the domain security group is created in it from IDs written to
SSM by hand, once, and read when the stack deploys:

| Parameter | Holds |
|---|---|
| `/flex/network/<environment>/vpc-id` | The VPC's ID |
| `/flex/network/<environment>/lambda-endpoint-security-group-id` | The security group of the VPC's Lambda interface endpoint |

The group lets nothing in. It lets a domain's function out only over HTTPS to the Lambda endpoint,
which is how a domain invokes gateways. The endpoint's own security group, which isn't the
platform's, must let the domain security group in.

### Permissions

Every domain has the same permissions, so they are in one role, with a permission boundary that
holds the same limits in case the role is ever widened by mistake. A domain's function may:

- invoke any function named `gateway-<environment>-*`, with any qualifier, such as `:live`. Any
  domain may call any gateway in its environment, and only gateways have that name;
- write to the domain log group, and use its key for that through CloudWatch Logs;
- create and remove the network interfaces Lambda needs to run it in the VPC.

The integration role may invoke only `function:domain-<environment>-*:live`, the alias each
release moves, and only API Gateway in the same account may assume it. So no domain's function
needs a resource policy of its own, and a function created again under the same name needs nothing
added.

API Gateway's logging role may write only to the domains' API access log groups,
`/flex/domain/<environment>/<domain>/api-access`, and to API Gateway's execution log groups. It
creates none: each domain's stack creates them first, encrypted.

## Routing a request

Planned. The domain's API answers every path and method under the domain's root, with `ANY` on
`/` and on `/{proxy+}`, and passes each request to the domain's function unchanged. The API checks
that the Frontdoor signed the request, and nothing about the path, method or body. The domain's
code decides which routes exist and how each is handled, and answers anything else itself, such as
with a 404.

So a domain adds or changes a route by releasing its code. No change to the platform's config or
stacks is needed.

## The domain's function

The function is named `domain-<environment>-<name>`, built by `domainFunctionName` in
`@repo/domain-infra`. Everything that refers to the function finds it by this name.

These are planned:

- **The function is created outside CloudFormation**, when the domain's code is first released.
  No platform deploy holds it, so none can replace the code, versions or alias a team released.
- **The platform sets what the external domain team can't set:** the execution role, the domain
  log group, the VPC's isolated subnets and the domain security group, and the environment
  variables, among them `FLEX_ENVIRONMENT`. `FLEX_ENVIRONMENT` names the environment, so that names built from it, such
  as a gateway's function name, match the environment the domain runs in. Code never branches on
  its value.
- **The domain's API invokes the function through its `live` alias,** by an ARN built from the
  name. Each release publishes a version and moves `live` to it, so the API reaches only code that
  was deliberately released, and moving the alias back rolls a release back. Until the first
  release there is no `live`, and the API answers 500.
- **The VPC's isolated subnet IDs come from SSM parameters,** written by hand like the VPC's ID.
