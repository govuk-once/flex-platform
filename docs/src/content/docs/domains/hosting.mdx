A domain is hosted from a line of the platform's config. Domain teams write the domain's code and
never write CDK. The platform provides everything the code runs with and behind.

The config and its checks are in `infra/app`, with the stacks. The constructs and the names they
use are in `domains/infra` (`@repo/domain-infra`).

## Declaring a domain

Each domain account in an environment lists the names of the domains it hosts in that environment:

```ts
domainAccounts: [
  {
    name: "domain00",
    account: "098640806149",
    domains: ["domain-a", "domain-b"],
    zone: {
      name: "development.flex-platform.once.service.gov.uk",
      id: "Z0835542Q6J8ILWJ1RGR",
    },
  },
],
```

The Frontdoor routes `/app/<name>/...` to a domain, and its resources are named from its name.
Config holds no routes, and nothing else about what the domain does. See
[routing a request](#routing-a-request).

A domain is hosted only in the environments that list it. Moving it to another domain account is
moving its name to that account's list.

<Aside type="caution" title="Moving a domain between accounts">
Moving a domain's name does not move its function or code. The destination account gets a new
domain stack, and the domain team must release the function there before it can serve requests.
The previous account's domain stack and its resources must be removed separately.
</Aside>

### Checks

Before building any stage, the app checks every domain:

- its name is 1 to 32 lowercase letters, digits and hyphens, starting with a letter and not
  ending with a hyphen;
- its name is used once in its environment, across all of the environment's domain accounts,
  since the Frontdoor routes by name alone;
- its function's name, `domain-<environment>-<name>`, is within Lambda's 64 characters. Each name
  is within 32 alone, but the two together can pass it.

## What a domain account provides

`DomainAccountStack`, `domain-<environment>-<account>`, holds what every domain in a domain account
shares in one environment. Nothing in it names a domain, so adding or removing one never changes
it. It is in eu-west-2, the region the edge signs requests for, and has termination protection:
deleting it would take the domains' execution and deploy roles and their certificate with it, and
leave the account's API Gateway logging setting naming a deleted role.

| Construct | Builds |
|---|---|
| `WildcardCertificate` | A CAA record at the zone's apex, `0 issue "amazon.com"`, so only Amazon may issue certificates for the zone. Then `*.<zone>`, validated through DNS in the account's own zone. |
| `PlatformLogGroup` | `/flex/domain/<environment>/function`, the log group every domain's function logs to |
| `ExecutionRole` | `domain-<environment>-execution`, the role every domain's function runs as, and its permission boundary. See [permissions](#permissions). |
| `DeployRole` | `domain-<environment>-deploy`, the role a release assumes to create and update a domain's function. See [permissions](#permissions). |
| `ApiGatewayLogging` | API Gateway's logging role, set on the account, so every API in it can write its access and execution logs |

One wildcard certificate serves every domain because ACM limits a certificate's first name to 64
characters. A certificate for `<domain>.<zone>` would leave a domain's name as few as 18.

ACM generates the certificate's ARN, so the stack writes it to SSM, at
`/flex/domain/<environment>/certificate-arn`.

### Network

Every domain runs in its domain account's [network](/flex-platform/infrastructure/network/), in
the isolated subnets, with no route to the internet. There is no setting to change this: a domain
reaches an upstream through a gateway, and a gateway that needs the internet has its own
[placement](/flex-platform/reference/glossary/#placement). The network creates the `domain`
security group a domain's function runs in, which may reach only the `lambda` endpoint: see
[what a workload may reach](/flex-platform/infrastructure/network/#what-a-workload-may-reach).

The stack reads two of the network's
[parameters](/flex-platform/infrastructure/network/#ids-other-stacks-read) when it deploys, and
holds the deploy role to them:

| Parameter | Holds |
|---|---|
| `/flex/network/<environment>/isolated-subnet-ids` | The isolated subnets' IDs |
| `/flex/network/<environment>/security-group/domain` | The `domain` security group's ID |

If the network is ever replaced, the stack deploys with `--force` to read the new IDs.

### Permissions

Every domain has the same permissions, so they are in one role, with a permission boundary that
holds the same limits in case the role is ever widened by mistake. A domain's function may:

- invoke any function named `gateway-<environment>-*`, with any qualifier, such as `:live`. Any
  domain may call any gateway in its environment, and only gateways have that name. The stack
  takes the pattern from `gatewayFunctionPattern` in `gateways/infra`;
- write to the domain log group, and use its key for that through CloudWatch Logs;
- send its traces to X-Ray;
- create and remove the network interfaces Lambda needs to run it in the VPC.

Lambda manages those network interfaces with the role's credentials, which the function's code
holds too. So the role denies the network interface actions to any call made from a domain's code,
which Lambda marks with the function's ARN. Lambda's own calls carry no function's ARN, so they
are still allowed.

The deploy role may be assumed only by principals in its own account that are themselves allowed
to assume it. It may create, configure, release and read functions named
`domain-<environment>-*`, describe the network Lambda checks a function's placement against, and
pass only the execution role, only to Lambda. It denies:

- every Lambda action on any function named `gateway-<environment>-*`;
- creating or configuring a domain's function with no VPC, in any subnet but the isolated ones, or
  with any security group but the `domain` group.

The denies hold whatever else the role is ever allowed, so a domain's function can only run where
the platform places it.

API Gateway's logging role may write only to the domains' API access log groups,
`/flex/domain/<environment>/<domain>/api-access`, and to API Gateway's execution log groups. It may
create none, so it writes only to log groups that already exist, encrypted.

## Routing a request

Planned. The domain's API answers every path and method under the domain's root, with `ANY` on
`/` and on `/{proxy+}`, and passes each request to the domain's function unchanged. The API checks
that the Frontdoor signed the request, and nothing about the path, method or body. The domain's
code decides which routes exist and how each is handled, and answers anything else itself, such as
with a 404.

So a domain adds or changes a route by releasing its code. No change to the platform's config or
stacks is needed.

## The domain's function

The function is named `domain-<environment>-<name>`, built by `domainFunctionName` in
`@repo/domain-infra`. Everything that refers to the function finds it by this name.

## Releasing a domain's function

A release creates and updates a domain's function as `domain-<environment>-deploy`. It sets:

- the name, `domain-<environment>-<name>`;
- the role, `domain-<environment>-execution`;
- the isolated subnets and the `domain` security group, from the network's parameters above. The
  deploy role refuses a configuration with no VPC, so a release sends them with every configuration
  update;
- logging to `/flex/domain/<environment>/function`;
- `FLEX_ENVIRONMENT`, the environment's name, which the code uses only to build names, such as a
  gateway's function name, and never to choose what it does;
- active tracing, so Lambda sends its traces to X-Ray.

Then it publishes a version and points the `live` alias at it. The deploy role can enforce the
function's name, role and network, but not its logging, environment or tracing, which only the
release sets.
