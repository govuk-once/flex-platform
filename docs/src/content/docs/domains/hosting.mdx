---
title: Hosting a domain
description: How a domain is declared in config, where its function runs, and what the platform provides around it.
---

A domain is hosted from a few lines of the platform's config. Domain teams write the domain's code
and never write CDK. The platform provides everything the code runs with and behind.

The config and its checks are in `infra/app`, and the names they use are in `domains/infra`
(`@repo/domain-infra`). Nothing deploys a domain. Each part of this page that is planned says so.

## Declaring a domain

Each domain account in an environment lists the domains it hosts in that environment:

```ts
domainAccounts: [
  {
    name: "domain00",
    account: "098640806149",
    domains: [{ name: "domain-a" }, { name: "domain-b", access: "private" }],
    zone: {
      name: "development.flex-platform.once.service.gov.uk",
      id: "Z0835542Q6J8ILWJ1RGR",
    },
  },
],
```

| Field    | Required | Holds                                                                                                 |
| -------- | -------- | ----------------------------------------------------------------------------------------------------- |
| `name`   | Yes      | The domain's name. The Frontdoor routes `/app/<name>/...` to it, and its resources are named from it. |
| `access` | No       | Where the domain's function runs: see [access levels](#access-levels).                                |

Config holds no routes, and nothing else about what the domain does. See
[routing a request](#routing-a-request).

A domain is hosted only in the environments that list it. Moving it to another domain account is
moving its entry to that account's list.

### Checks

Before building any stage, the app checks every domain:

- its name is 1 to 32 lowercase letters, digits and hyphens, starting with a letter and not
  ending with a hyphen;
- its name is used once in its environment, across all of the environment's domain accounts,
  since the Frontdoor routes by name alone;
- its function's name, `domain-<environment>-<name>`, is within Lambda's 64 characters. Each name
  is within 32 alone, but the two together can pass it.

## Access levels

A domain's access level decides where its function runs, and so what it can reach:

| Level      | Function runs in           | Can reach                                                                        |
| ---------- | -------------------------- | -------------------------------------------------------------------------------- |
| `isolated` | The VPC's isolated subnets | Gateways and AWS services through the VPC's endpoints. No route to the internet. |
| `private`  | The VPC's private subnets  | The internet, through NAT                                                        |
| `public`   | Outside the VPC            | The internet, directly                                                           |

The default is `isolated`, so a domain reaches gateways and nothing else unless its config says
otherwise.

## Routing a request

Planned. The domain's API answers every path and method under the domain's root, with `ANY` on
`/` and on `/{proxy+}`, and passes each request to the domain's function unchanged. The API checks
that the Frontdoor signed the request, and nothing about the path, method or body. The domain's
code decides which routes exist and how each is handled, and answers anything else itself, such as
with a 404.

So a domain adds or changes a route by releasing its code. No change to the platform's config or
stacks is needed.

## The domain's function

The function is named `domain-<environment>-<name>`, built by `domainFunctionName` in
`@repo/domain-infra`. Everything that refers to the function finds it by this name.

These are planned:

- **The function is created outside CloudFormation**, when the domain's code is first released.
  No platform deploy holds it, so none can replace the code, versions or alias a team released.
- **The platform provides everything around it:** its execution role, its log group, its
  placement for its access level, and its environment variables, among them `FLEX_ENVIRONMENT`.
  `FLEX_ENVIRONMENT` names the environment, so that names built from it, such as a gateway's
  function name, match the environment the domain runs in. Code never branches on its value.
- **The domain's API invokes the function through its `live` alias,** by an ARN built from the
  name. Each release publishes a version and moves `live` to it, so the API reaches only code that
  was deliberately released, and moving the alias back rolls a release back. Until the first
  release there is no `live`, and the API answers 500.
- **The VPC's subnet and security group IDs come from SSM parameters,** read when a stack
  deploys. The VPC isn't the platform's, so its IDs are not in config.
