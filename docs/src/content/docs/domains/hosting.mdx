A domain is hosted from a line of the platform's config. Domain teams write the domain's code and
never write CDK. The platform provides everything the code runs with and behind.

The config, its checks and the stacks are in `infra/app`, with a
[stack](/flex-platform/infrastructure/overview/#stacks) for every domain account and every domain.
The constructs and the names they use are in `domains/infra` (`@repo/domain-infra`).

## Declaring a domain

Each domain account in an environment lists the domains it hosts in that environment, each by its
name, or as `{ name, disabled: true }` when it is [disabled](#disabling-a-domain):

```ts
domainAccounts: [
  {
    name: "domain00",
    account: "098640806149",
    domains: [
      "domain-a",
      { name: "domain-b", disabled: true },
    ],
    zone: {
      name: "development.flex-platform.once.service.gov.uk",
      id: "Z0835542Q6J8ILWJ1RGR",
    },
    network: { availabilityZones: ["eu-west-2a", "eu-west-2b"] },
    gateways: [],
  },
],
```

The Frontdoor routes `/app/<name>/...` to a domain, and its resources are named from its name.
Config holds no routes, and nothing else about what the domain does. See
[routing a request](#routing-a-request).

A domain is hosted only in the environments that list it. Moving it to another domain account is
moving its name to that account's list.

The stage lists the domain too, once, in its own `domains`, whichever of its environments host
it. The entry names the GitHub repository that may [release](#releasing-a-domains-function) the
domain, by GitHub's IDs for the repository and its owner, or `null` until the repository exists:

```ts
domains: [
  {
    name: "domain-a",
    repository: { name: "example-org/domain-a", id: "700000001", ownerId: "800000001" },
  },
  { name: "domain-b", repository: null },
],
```

`gh api repos/<owner>/<repository> --jq '.id, .owner.id'` prints the two IDs.

<Aside type="caution" title="Moving a domain between accounts">
Moving a domain's name does not move its function or code. The destination account gets a new
domain stack, and the domain team must release the function there before it can serve requests.
The previous account's domain stack and its resources must be removed separately.
</Aside>

### Disabling a domain

List a domain as `{ name, disabled: true }` to stop routing to it. Its stack stays as it is, with
its API, its host, its log groups and its name, which no other account in the environment may
take. The Frontdoor's routes leave it out, so a request for it, once its token is verified, gets
the 404 an unknown domain gets, and never reaches its API. Listing it by its name again restores
the route and recreates nothing. Release the function the route will reach before enabling it.

Disabling withdraws the route and nothing else: it doesn't stop an invocation already running, or
change what the function's role may do. The routes change when the Frontdoor's stack deploys, and
copies of Lambda@Edge can route to the domain until the new version has replaced them.

Removing a domain from config is different. Its stack leaves the app, and CDK doesn't delete a
stack the app no longer builds, so it is deleted by hand, once its
[termination protection](/flex-platform/infrastructure/overview/#stacks) is turned off. Its log
groups are retained, so adding the domain back later fails until they are imported into its new
stack or deleted.

### Checks

Before building any stage, the app checks every domain, disabled ones included:

- its name is 1 to 32 lowercase letters, digits and hyphens, starting with a letter and not
  ending with a hyphen;
- its name is used once in its environment, across all of the environment's domain accounts,
  since the Frontdoor routes by name alone;
- it is in its stage's `domains`, once, and every domain there is hosted in at least one of the
  stage's environments;
- it is hosted in the environment its own environment's `release` promotes from, if it promotes;
- its execution role's name, `domain-<environment>-<name>-execution`, is within IAM's 64
  characters. It is the longest of the names Lambda and IAM limit, so the others fit too. Each name
  is within 32 alone, but the two together can pass it: together they may be 46 at most.

## What a domain account provides

`DomainAccountStack`, `domainaccount-<environment>-<account>`, holds what every domain in a domain
account shares in one environment. Nothing in it names a domain, so adding or removing one never
changes it. It is in eu-west-2, the region the edge signs requests for, and has termination
protection: deleting it would take the domains' certificate with it, and leave the account's API
Gateway logging setting naming a deleted role.

| Construct | Builds |
|---|---|
| `WildcardCertificate` | A CAA record at the zone's apex, `0 issue "amazon.com"`, so only Amazon may issue certificates for the zone. Then `*.<zone>`, validated through DNS in the account's own zone. |
| `ApiGatewayLogging` | API Gateway's logging role, set on the account, so every API in it can write its access and execution logs |

One wildcard certificate serves every domain because ACM limits a certificate's first name to 64
characters. A certificate for `<domain>.<zone>` would leave a domain's name as few as 18.

ACM generates the certificate's ARN, so the stack writes it to SSM, at
`/flex/domain/<environment>/certificate-arn`, where each domain's stack reads it when it deploys. If
the certificate is ever replaced, each domain's stack deploys with `--force` to read the new ARN,
and CloudFormation can't delete the old certificate while a domain's custom domain still uses it.

API Gateway's logging role has AWS's managed policy, `AmazonAPIGatewayPushToCloudWatchLogs`, so it
may create, write to and read any log group in the account and region. API Gateway refuses a
logging role with less: it checks the role's effective permissions, so it refuses one scoped to the
domains' log groups, or one denied `logs:CreateLogGroup`. Every API's log groups are created by its
own stack instead, before its stage, so API Gateway never creates one.

## What a domain provides

`DomainStack`, `domain-<environment>-<domain>`, holds one domain's API and the host it answers at,
and the log group and roles its function runs and is released with, in the domain account that
hosts it, in eu-west-2. It holds no function: the API reaches the domain's function by name. A
domain [removed from config](#disabling-a-domain) keeps its stack until someone deletes it.

| Construct | Builds |
|---|---|
| `ProxyApi` | `domain-<environment>-<domain>-api`, a regional REST API whose `execute-api` address is turned off, with its resource policy, its `ANY` methods, its stage, `default`, its access and execution log groups, the role it invokes the function through, its gateway responses, and its [refusal alarms](#watching-refusals) |
| `ApiHost` | `<domain>.<zone>`, with the domain account's wildcard certificate, mapped to the stage at its root, and its alias record in the account's zone |
| `PlatformLogGroup` | `/flex/domain/<environment>/<domain>/function`, the log group the domain's function logs to |
| `ExecutionRole` | `domain-<environment>-<domain>-execution`, the role the domain's function runs as, and its permission boundary. See [permissions](#permissions). |
| `DeployRole` | `domain-<environment>-<domain>-deploy`, the role a release assumes to create and update the domain's function. See [permissions](#permissions). |

The stage is traced with X-Ray, logs errors, and never logs request or response bodies. Its access
logs go to `/flex/domain/<environment>/<domain>/api-access`, one JSON line per request. Its
execution logs go to `API-Gateway-Execution-Logs_<api id>/default`, which the stack creates before
the stage, so it is encrypted and kept for a year, and API Gateway never creates it first. The stage has no
throttling of its own, so it shares the account's limits.

### Network

Every domain runs in its domain account's [network](/flex-platform/infrastructure/network/), in
the isolated subnets, with no route to the internet. There is no setting to change this: a domain
reaches an upstream through a gateway, and a gateway that needs the internet has its own
[placement](/flex-platform/reference/glossary/#placement). The network creates the `domain`
security group a domain's function runs in, which may reach only the `lambda` endpoint: see
[what a workload may reach](/flex-platform/infrastructure/network/#what-a-workload-may-reach).

The stack reads three of the network's
[parameters](/flex-platform/infrastructure/network/#ids-other-stacks-read) when it deploys. It
holds the deploy role to the first two, which the deploy role may read too, so a release places a
function from the same values. It holds the execution role to the third:

| Parameter | Holds |
|---|---|
| `/flex/network/<environment>/isolated-subnet-ids` | The isolated subnets' IDs |
| `/flex/network/<environment>/security-group/domain` | The `domain` security group's ID |
| `/flex/network/<environment>/endpoint/lambda` | The `lambda` endpoint's ID |

If the network is ever replaced, the stack deploys with `--force` to read the new IDs.

### Permissions

Each domain's function runs as a role of its own, `domain-<environment>-<domain>-execution`. It
may:

- invoke any function named `gateway-<environment>-*`, through its `live` alias and no other way.
  Any domain may call any gateway in its environment, and only gateways have that name. The stack
  takes the pattern from `gatewayAliasPattern` in `gateways/infra`, as the network's
  [`lambda` endpoint](/flex-platform/infrastructure/network/#endpoints) does;
- write to its own domain's log group, `/flex/domain/<environment>/<domain>/function`, and use
  its stack's key for that through CloudWatch Logs;
- send its traces to X-Ray;
- create and remove the network interfaces Lambda needs to run it in the VPC.

It may invoke a gateway only through the network's `lambda` endpoint. A domain's code holds the
role's credentials, and could give them away in a response or a log line. So the role denies
invoking any function by any other way, and the credentials invoke nothing from outside the
network.

Lambda manages those network interfaces with the role's credentials, which the function's code
holds too. So the role denies the network interface actions to any call made from a domain's code,
which Lambda marks with the function's ARN. Lambda's own calls carry no function's ARN, so they
are still allowed.

No domain's role may write to another's log group, so the log group a line is in shows which
domain wrote it. A stream's name doesn't: Lambda names each stream, but a domain's code can write
a stream under any name.

The role runs code that teams outside the platform write, with that code holding its credentials.
So it has a permission boundary that holds the same statements. Whatever policy is ever attached to
the role, by mistake or by hand, a domain's code can do no more than the boundary allows. The deploy
role has none: it runs no one's code, and its denies already hold whatever else it is ever allowed.

Each domain has a deploy role too, `domain-<environment>-<domain>-deploy`. Only the stage's
release worker may assume it. The role trusts the stage's shared account, on the condition that
the caller is the worker's role, `shared-release-worker`: IAM refuses a principal that doesn't
exist yet, so the trust names the role by a condition. It may create,
configure, release and read only its domain's function, with the function's versions and aliases,
read the two network parameters above, describe the network Lambda checks a function's placement
against, read its own domain's bundles in the [code bucket](#uploading-a-bundle), and pass only its
domain's execution role, only to Lambda. Lambda reads the bundle a function is created or updated
from as the caller, so the role must be able to read it. The bucket lets every deploy role read any
bundle, so the role's own policy is what holds a release to its domain's code. So no release can
give a function another domain's role, and with it another domain's log group. It denies:

- every Lambda action on any function named `gateway-<environment>-*`;
- creating or configuring a domain's function with no VPC, in any subnet but the isolated ones, or
  with any security group but the `domain` group.

The denies hold whatever else the role is ever allowed, so a domain's function can only run where
the platform places it.

### Who can call it

Every method uses IAM authorisation, and synth fails for any API Gateway method in the app without
it: see [checks](/flex-platform/infrastructure/overview/#checks). The Frontdoor signs each request
with SigV4 as its edge role. The resource policy allows the Frontdoor's account only when the
caller is that role, and denies everyone else, so a principal in the domain account with
permission to invoke APIs is refused too.

The policy names the role in a condition, never as a principal, because API Gateway refuses a
policy that names a role that doesn't exist yet.

### Watching refusals

Each API counts IAM authorisation's refusals from its access log's `errorResponseType`, in the
namespace `flex/domain/<environment>/<domain>/api`, and alarms when they are sustained:

| Metric | Counts | Alarm | Goes off at |
|---|---|---|---|
| `bypass-attempts` | `MISSING_AUTHENTICATION_TOKEN` and `ACCESS_DENIED`: a request sent unsigned, or signed by anyone but the edge role | `domain-<environment>-<domain>-api-bypass-attempts` | 10 or more in each of three five-minute periods in a row |
| `signing-faults` | `INVALID_SIGNATURE` and `EXPIRED_TOKEN`: a signature that doesn't verify | `domain-<environment>-<domain>-api-signing-faults` | 1 or more in each of three five-minute periods in a row |

The host is in a public zone, so scanners find it, and the bypass alarm is set above that
background. A fault in the edge's signing refuses every request the edge sends, so any sustained
count of signing faults is one.

The metrics divide refusals by type, not by who sent them. A direct caller can send a signature
that doesn't verify, which counts as a signing fault, and the edge role refused by a mistake in
the resource policy counts as a bypass attempt. The alarms have no action until the platform has
alerting, so they notify no one: someone has to look at them.

### Investigating an origin refusal alarm

1. In Logs Insights, query `/flex/domain/<environment>/<domain>/api-access` for the alarm's
   `errorResponseType` values in its period. Note when they started and how many there were.
2. For signing faults, check whether requests through the Frontdoor are failing too: the
   Frontdoor answers them with `x-rejected-by: api-gateway`, and
   `/flex/frontdoor/<environment>/origin-request`, in the frontdoor account in eu-west-2, logs
   `origin_request_forwarded` for them at the same time. If so, the edge's signing is broken. Look
   for a recent change to the edge function, its role or this API, and roll it back. If Frontdoor
   traffic is being served, the signatures are someone else's: treat them as bypass attempts.
3. For bypass attempts, check first whether requests through the Frontdoor are refused too: a 403
   `auth_error` with `x-rejected-by: api-gateway`, while the edge logs `origin_request_forwarded`.
   If so, the API's resource policy no longer allows the edge role: check the domain's stack for
   drift, and deploy it again. Otherwise, judge the volume and pattern. A scanner's requests are
   few and spread out. A sustained stream of requests, signed especially, is a security incident.
   Escalate it with the log lines as evidence.

### Errors

When API Gateway refuses a request itself, it answers in the same shape as the Frontdoor, with
`x-rejected-by: api-gateway`, as the Frontdoor's own refusals name the part that refused:

| Response | Status | Body |
|---|---|---|
| Unauthorised, access denied, invalid signature, missing authentication token, expired token | 401 or 403 | `{"message":"Unauthorized","type":"auth_error"}` |
| Throttled | 429 | `{"message":"Too many requests","type":"client_error"}` |
| Any other 4xx | 4xx | `{"message":<API Gateway's own message>,"type":"client_error"}`. Its messages are fixed, so no caller's text reaches the body. |
| Any 5xx | 5xx | `{"message":"Internal server error","type":"server_error"}` |

A response from the domain's own code passes through unchanged.

### TLS

The custom domain uses `SecurityPolicy_TLS13_1_2_PFS_PQ_2025_09` in `STRICT` mode. It offers
TLS 1.3 and still accepts TLS 1.2 with forward secrecy. Only CloudFront reaches the host, over
IPv4, so it has one A record.

## Routing a request

The domain's API answers every path and method under the domain's root, with `ANY` on `/` and on
`/{proxy+}`, and passes each request to the domain's function unchanged. The API checks that the
Frontdoor signed the request, and nothing about the path, method or body. The domain's code decides
which routes exist and how each is handled, and answers anything else itself, such as with a 404.

So a domain adds or changes a route by releasing its code. No change to the platform's config or
stacks is needed.

The API invokes the function's `live` alias, by an ARN built from the function's name, through a
role of its own. Only API Gateway may assume the role, only a principal in the domain account can
set it on an API, and it may invoke only that domain's `live` alias. The role's trust carries no
`aws:SourceAccount` condition: API Gateway sends none when it assumes an integration's role, so the
condition would refuse every request. So the function needs no resource policy, and a function
created again under the same name needs nothing added. Each release publishes a version and moves
`live` to it, so the API reaches only code that was deliberately released, and moving the alias
back rolls a release back. Until the first release there is no `live`, and the API answers 500.

## The domain's function

The function is named `domain-<environment>-<name>`, built by `domainFunctionName` in
`@repo/domain-infra`. Everything that refers to the function finds it by this name.

## Releasing a domain's function

A domain's code is uploaded once, as a bundle, and released from the bucket it is kept in. Config
says which way code reaches each environment, in its `release`: `"publish"` where new code enters
the stage, or `{ promoteFrom }`, naming the environment whose released code it takes. In
platform-prod, `development` publishes, `staging` promotes from `development`, and `production`
from `staging`. The repository the stage's `domains` names for a domain is the only one that can
release it.

Where an environment publishes, the domain's pipeline [uploads a bundle](#uploading-a-bundle)
and then [asks for its release](#releasing-a-bundle), both through the
[pipeline API](#the-pipeline-api). Promotion, which takes released code from one environment to
the next, is planned.

### The release worker

A function in the shared account, `shared-release-worker`, does each release, so the pipeline API
can answer one at once. A first release creates a function in a VPC, which Lambda can take
minutes to make ready. The API puts each release on a FIFO queue, `shared-release.fifo`, grouped
by environment and domain, so one domain's releases there run one at a time, in the order they
were asked for, and other domains' run alongside. The worker and the queue are built by
`ReleaseWorker` in `shared/infra`, and its code is in `shared/release`.

#### The release table

The API records each release in a DynamoDB table, `shared-releases`, before it queues it, and the
worker records how it went. A release is kept under its domain in its environment, partition key
`target` (`<environment>/<domain>`), by its ID, sort key `id`. The ID is a UUID of version 7,
whose first 48 bits are the time the API made it, so the IDs sort in the order releases were
asked for, and a domain's releases list newest first. Each holds:

| Attribute | Holds |
|---|---|
| `environment`, `domain`, `sha256`, `versionId` | What was asked for: the bundle by its hash, and the version of its object |
| `runId`, `commit` | The run that asked, and its commit, when its token said |
| `status` | `queued`, `releasing`, `released`, `failed`, `refused` or `abandoned` |
| `requestedAt`, `updatedAt` | When the API recorded it, and when it last changed, in milliseconds |
| `attempts` | How many times the worker has claimed it |
| `step`, `reason` | For a release that stopped: the step, and a fixed code for why |
| `version`, `created`, `moved` | For a release that succeeded: the version `live` points at, and whether the release created the function and moved `live` |

`failed` will be tried again. `refused` never will be: nothing about the release would change.
`abandoned` was tried as often as the queue tries, and won't be again: the pipeline asks again.
`released` and `refused` are final. `abandoned` isn't, because the worker still runs a release
its queue gives it (see [the dead-letter worker](#the-dead-letter-worker)). The table is the
record of each request and how it went.
What is deployed is Lambda's to say: the worker reads it at each step, and the table follows it.
The table is retained, with point-in-time recovery, and deletion protection is on.

#### Who can ask for a release

Only the pipeline API, for a pipeline it has [allowed](#what-the-api-checks). Anything that IAM
lets invoke the worker can write its event, and a function's own policy holds no deny that could
refuse it. So a message holds only a release's key, its environment, domain and ID, and the
worker releases what the table records under it:

- **Only the API records a release, and nothing changes what it asked for.** The table's policy
  denies, to every principal, putting an item unless it is the API's role, `shared-ci`, changing
  one unless it is `shared-ci`'s, `shared-release-worker`'s or
  `shared-release-dead-letter-worker`'s, and deleting one. It also denies, to every principal, an
  update that names `environment`, `domain`, `sha256`, `versionId`, `runId`, `commit` or
  `requestedAt`. So no writer can point a release at another domain or another bundle, and an
  update that makes an item makes one with none of them, which isn't a release. PartiQL's writes
  are denied outright, since nothing uses them. A deny in a resource's policy holds whatever any
  other policy allows. A message that names no release in the table is logged and dropped.
- **A final release isn't run again.** Before each attempt, the worker claims the release: it
  marks it `releasing` and counts the attempt, unless it is final. So a message sent again,
  however it was got, runs nothing that is released or refused. Any other release may be tried
  again, even while an attempt runs: every step reads Lambda before it acts, so an attempt at what
  is done changes nothing, and Lambda refuses a change to a function it is still changing.
- **The queue takes messages only from the API, and gives them only to the worker.** Its policy
  denies, to every principal, sending a message unless it is `shared-ci`'s role, taking one
  unless it is `shared-release-worker`'s, purging the queue, and moving messages out of either
  queue. Only the release queue may use the dead-letter queue, and no principal may send to it:
  SQS moves a message there itself.

No release can roll a domain back. `live`'s description names the release that set it, and the
worker changes nothing for a release whose ID sorts before that one, which is one asked for
earlier. A rollback is a new release, of the older bundle.

#### What a release does

For each release it claims, the worker:

1. **Assumes the domain's deploy role** in the domain account, and reads `live`. A release `live`
   already names is done: the worker records it `released`, with `live`'s version, and changes
   nothing. A release asked for before the one on `live` is refused.
2. **Checks the bundle.** It reads the version of the bundle's object the API found, in full,
   and hashes it. The key names the bundle's hash, so an object with any other is refused before
   anything is made of it. It reads the isolated subnets and the `domain` security group from the
   network's parameters, as the role.
3. **Creates the function,** the first time, and waits until it is active. Otherwise it waits
   while Lambda is making or changing the function, then updates its configuration, waits,
   updates its code and waits again. Lambda refuses a change to a function it is still changing.
   It updates the function whatever state it settles in: an update reactivates one idle long
   enough to be `Inactive`, and may mend one that `Failed`.
4. **Checks the code Lambda loaded.** Lambda's hash of the code, in base64, must be the bundle's,
   in hex, compared as bytes.
5. **Publishes a version,** if the code still has that hash, and waits until it is active. A
   version's description names the bundle and the commit it was built from. A function whose code
   and configuration haven't changed since its last version gets that version back.
6. **Points `live` at the version,** creating the alias the first time, and names the release in
   its description. Otherwise it checks the order again, and moves the alias only from the
   revision it read, so a change made since is never overwritten.

Nothing reaches the new code until the last step.

An attempt has 15 minutes, the worker's timeout. Its waits share them, less 30 seconds kept back to
move `live` and record how the attempt went, so a first create in a VPC, which Lambda can take
minutes to make ready, can use most of them. A wait that runs out fails the attempt.

A release sets the function's:

- name, `domain-<environment>-<name>`;
- role, `domain-<environment>-<name>-execution`;
- isolated subnets and `domain` security group. The deploy role refuses a configuration with no
  VPC, so a release sends them with every configuration update;
- logging, to `/flex/domain/<environment>/<name>/function`;
- `FLEX_ENVIRONMENT`, the environment's name, which the code uses only to build names, such as a
  gateway's function name, and never to choose what it does;
- tracing, active, so Lambda sends its traces to X-Ray;
- runtime, `nodejs24.x`, on arm64, with the handler `index.handler`, 1,024 MB of memory and a
  29-second timeout. A domain doesn't choose these. The timeout is how long the domain's API
  waits for the function, so a function never runs on after no one is waiting;
- code, the bundle's object by its version. Lambda reads the code from the bucket in place and
  keeps no copy, so the bucket [lets Lambda read it](#uploading-a-bundle) for as long as the
  function has it.

The deploy role enforces the function's name, role and network, but not its logging,
environment or tracing, which only the release sets. A release that set another log group would
lose the function's logs, since its role may write to no other.

The worker records how each release went in the table. A release that fails with something that
might go differently next time, such as an AWS error, is recorded `failed` and given back to the
queue, which delivers it again after 20 minutes. After three attempts it is moved to the
dead-letter queue, `shared-release-dead-letter.fifo`, where the
[dead-letter worker](#the-dead-letter-worker) gives it up. A release that can never succeed, such
as a bundle whose bytes aren't what its key says, or a release older than `live`'s, is recorded
`refused` and dropped.

The worker records each outcome before it lets the message go, and only over the claim it made,
so it never overwrites what another writer recorded since. `released` is the exception: Lambda
says what is live, so it is recorded over anything but `released`. A worker that stops before it
finishes, by running out of time or memory, records nothing: the release stays `releasing`, and
the queue delivers the message again after 20 minutes, to an attempt that picks up where Lambda
shows the last one stopped.

The worker writes one log line for each attempt at a release, to `/flex/shared/release-worker`:
what happened as a fixed code, the queue's ID for the message, how long it took, and, once the
table holds the release, its ID, the environment, the domain, the bundle's hash, GitHub's ID for
the run and the commit. A release that stopped adds the step and a reason: AWS's code for the
error, such as `AccessDeniedException`, or Lambda's for a function that won't become ready, such
as `SubnetOutOfIPAddresses`, never a message. A release that succeeded adds the version, and
whether it created the function and moved `live`.

The worker is built with each domain it may release, and everything a release of it names, by
`buildReleaseWorker` when the stage is synthesized: every domain with a repository, in each
environment that publishes. Its role may take the queue's messages, read and change a release in
the table, read bundles, and assume those domains' deploy roles, and nothing else.

### The dead-letter worker

A function of its own, `shared-release-dead-letter-worker`, reads the dead-letter queue, so the
release table says when no more attempts are coming. The release worker can't say so itself: an
attempt that stopped with its function recorded nothing. For each message, it reads the release
and, unless it is final or given up already, records it `abandoned`, keeping the step and reason
its last attempt stopped at. It logs `release_abandoned` with how many attempts there were. A
release final or given up already is left as it is. An attempt still running may yet release it:
Lambda says what is live, so the worker records `released` over `abandoned`.

Anything that IAM lets invoke the function can write its event, and nothing in an event shows that
the queue gave the release up. So `abandoned` isn't final: the release worker still claims and runs
a release its queue gives it. A release given up by an event the queue didn't send is still run, and
the alarm is all that shows it was given up. A message the queue really moves to the dead-letter
queue never returns to the release queue, since no principal may move one back.

It records first and lets the message go after. Lambda deletes a message only once the function
returns without giving it back, so a function that stops between the two leaves the message to
come again, and the second time finds the release already `abandoned`. A message it can't
record, because the table failed, it gives back, and logs `release_failed` at the step `abandon`.
The dead-letter queue has no queue behind it: such a message comes again every two minutes, until
it is recorded or the queue drops it after 14 days.

It is a separate function from the release worker so that it needs none of the worker's access.
Its role may take the dead-letter queue's messages and read and change a release, and nothing
else, and the queue's policy denies taking a message to every other role. It has a 30-second
timeout. Lambda holds a queue's visibility timeout to at least its reader's timeout, so the
dead-letter queue's can be two minutes, rather than the release worker's 20. It is built by
`ReleaseDeadLetterWorker` in `shared/infra`, and logs to `/flex/shared/release-dead-letter-worker`.

#### When a release is abandoned

Two alarms watch the dead-letter worker's log, with no action until the platform has alerting.
Each counts lines of one event into the namespace `flex/shared/release`, and goes off on any in
five minutes:

| Alarm | Goes off on | Means |
|---|---|---|
| `shared-release-abandoned` | `release_abandoned` | A release was given up. The table holds the step and reason its last attempt stopped at, and the release worker's log, `/flex/shared/release-worker`, has each attempt under the release's ID. |
| `shared-release-abandon-failed` | `release_failed` | A release couldn't be recorded as given up, so the table still says it may be tried. Its message is going round the dead-letter queue. |

The pipeline that asked sees `abandoned` and can ask again, once whatever stopped the release is
put right.

### The pipeline API

A domain's pipeline uploads and releases its code through an API of the platform's, never
through AWS itself, so it holds no AWS credentials. The API answers under `/ci`, at the apex of
the stage's shared zone, behind a CloudFront distribution of its own.

A job proves which repository it runs in with the token GitHub issues it, asked for with the
API's address, `https://<shared zone>/ci`, as its audience. It sends the token alone as
`x-flex-ci-token`, and not as `Authorization`: CloudFront signs each request for the API, and
that header holds its signature.

#### The distribution

Each stage has one, in its shared account, built by `ManagementEdge` in `shared/infra` from the
constructs [the Frontdoor's](/flex-platform/frontdoor/overview/#the-distribution) is built from.
It has the same TLS policy, sets the same security
[headers on every response](/flex-platform/frontdoor/overview/#response-headers), has the same
[web ACL rules](/flex-platform/frontdoor/overview/#waf), and caches nothing. Three things differ:

- **The rate limits.** One token may make 100 requests in five minutes and one address 500. The
  token's limit counts the exact value of `x-flex-ci-token`, and the web ACL keeps that header
  out of its logs and samples.
- **The origin.** Every path goes to the API's function, at its Lambda function URL. The URL
  takes only requests signed with SigV4 by a caller IAM allows, and the function's policy admits
  CloudFront alone, for the shared account's distributions. CloudFront signs every request it
  forwards, so a request sent straight to the URL from outside the shared account is refused
  before the function runs. In the account, as for any function, a principal whose own policy
  allows the call can make it. The function relies on the token it verifies either way. A synth
  [check](/flex-platform/infrastructure/overview/#checks) refuses a function URL with any other
  authorisation.
- **What the origin sees.** Every header the caller sent except `host`, and the
  `x-correlation-id` the CloudFront Function set. No cookie or query string. The function URL
  answers only to its own host. The headers aren't held to a list, because CloudFront refuses
  `x-amz-content-sha256` in one, and signs with it.

Its access logs, the web ACL's logs and the function's go to log groups in us-east-1, as
[the Frontdoor's](/flex-platform/frontdoor/overview/#logs) do.

#### The first check

A CloudFront Function, `shared-management-viewer-request`, runs on each request as it arrives,
after WAF. Its code is in `shared/viewer-request`. It checks a request's structure as
[the Frontdoor's](/flex-platform/frontdoor/cloudfront-function/) does, sharing its code for each
check they have in common, with the same ID,
[rejections](/flex-platform/frontdoor/cloudfront-function/#rejections) and
[log line](/flex-platform/frontdoor/cloudfront-function/#logs). It verifies no signature:
[the API does](#what-the-api-checks). In order, the function:

1. **Gives the request its ID,** as `x-correlation-id`, and removes any trace context and every
   `x-flex-` header the caller sent but the token's.
2. **Checks the method.** Only `POST` passes. Anything else is a 405 with an `Allow` header.
3. **Checks the token's shape.** `x-flex-ci-token` appears once, and is one token of at most
   8 KB in three base64url segments, each written the one way its bytes encode. The header and
   payload are JSON objects. `alg` is `RS256`, `iss` is GitHub Actions' issuer, `aud` is the
   API's address, and `exp` is a finite time in the future. A failure is a 401,
   before the path is looked at.
4. **Checks the path.** It is under `/ci/`, with no empty or dot segment and no encoded `/`, `\`
   or `.`. Anything else is a 404. Which paths the API serves is for the API.
5. **Checks the content type.** The body is `application/json`. Anything else is a 415.
6. **Checks the body's hash is there.** `x-amz-content-sha256` appears once, and is 64 lowercase
   hex digits. Anything else is a 400, `Bad request`. CloudFront can't hash a body, so it signs
   the hash the caller sends, and the API's origin refuses a body with any other.

The issuer and the audience are baked into the function by `buildViewerRequestFunction`, as the
Frontdoor's function has [its issuers](/flex-platform/frontdoor/cloudfront-function/#building-the-function).

#### What the API checks

The API is one Lambda function, `shared-ci`, in eu-west-2. Its code is in `shared/ci`. For each
request, in order, it:

1. **Verifies the token.** It checks the signature against the keys GitHub publishes, and that
   the token is in the one encoding the CloudFront Function accepts. `iss` is GitHub Actions'
   issuer, `aud` is the API's address, `alg` is `RS256`, `exp` is present and in the future,
   and `nbf`, if present, has passed. `repository_id` and `repository_owner_id` are each digits.
   A failure is a 401. The keys are fetched, kept for 10 minutes and fetched again as
   [Lambda@Edge keeps its issuers'](/flex-platform/frontdoor/lambda-edge/#verifying-the-token),
   and a request that needs keys it can't fetch gets a 500, never a pass.
2. **Finds the route.** A path that is no route's is a 404, and a route's path with a method it
   doesn't take is a 405, with an `Allow` header naming the ones it does. Both come after the
   token, so a caller without one learns nothing of the routes. There are two, both `POST`:
   `/ci/environments/<environment>/domains/<domain>/uploads` and
   `/ci/environments/<environment>/domains/<domain>/releases`. Each route is a method, a path and
   its handler, in `shared/ci/src/function/routes/`. Every route's path names an environment and a
   domain, and the router refuses to start with one that doesn't.
3. **Decides whether this pipeline may act on that domain there,** the same for every route, so no
   route can leave it out. A caller of another kind gets a function of its own. Anyone with a GitHub
   repository can have GitHub sign a token for the API's address, so a verified token says only
   which repository's pipeline is calling. The pipeline is allowed when:
   - the stage has the environment, and the environment hosts the domain;
   - the token's `repository_id` and `repository_owner_id` are the ones the stage's
     [config](/flex-platform/infrastructure/overview/#config) holds for the domain. Both, so a
     repository transferred to another owner is no longer the one registered. A domain with no
     repository in config can't be released;
   - the token's `environment` is the path's. GitHub sets that claim only for a job that runs
     in the GitHub environment of that name, once the repository's own protection rules for it
     have passed. So a domain's repository has a GitHub environment named for each of the
     platform's environments it releases to, and decides there which jobs may reach each.

   Nothing is decided by the token's `sub`, whose format a repository's admin can change. A
   refusal is a 403, the same whatever the reason, so a pipeline learns nothing of which
   environments and domains exist, or which repository a domain belongs to.
4. **Checks the environment publishes.** New code enters a stage only where an environment's
   `release` is `"publish"`. Anywhere else is a 409, `This environment takes no uploads` or
   `This environment takes no releases`: the pipeline is allowed, so it is told why.
5. **Reads the body.** For an upload it is
   `{ "sha256": "<64 lowercase hex digits>", "size": <bytes> }`, with a size from 1 byte to
   250 MB, the most Lambda unzips a function's code to. For a release it is
   `{ "sha256": "<64 lowercase hex digits>" }`. Either holds nothing else, and anything else is a
   400. The body is read only now, for a pipeline that is allowed.
6. **Signs the upload,** and answers 200 with [where to send the bundle](#uploading-a-bundle),
   or **queues the release** of a bundle that was uploaded, and answers 202. See
   [releasing a bundle](#releasing-a-bundle).

The issuer, the audience, the environments, whether each publishes, each domain's repository,
the bucket, the release table's name and the release queue's address are baked into the function
by `buildCiFunction` when the stage is synthesized. So who may release a domain changes only by a
change to config and a deploy of `shared-release`.

The function writes one log line for each request: what happened as a fixed code, the request's
trace ID, how long it took, and for a verified token GitHub's IDs for the repository, its owner
and the workflow run, and the commit the job runs for. The environment and the domain are logged
only for a pipeline that was allowed, when they are names from config. A signed upload's line
adds the bundle's key and size, and a queued release's the bundle's key and its object's
version. The token is never logged, and neither is the address an
upload was signed for, or anything a repository's admin can write, such as its name or an
environment's.

#### Uploading a bundle

A domain's code is uploaded as one zip, its bundle, in two requests. The pipeline asks the API
where to send the bundle, saying what it will send:

```http
POST /ci/environments/<environment>/domains/<domain>/uploads
content-type: application/json
x-flex-ci-token: <the job's token>
x-amz-content-sha256: <this body's SHA-256>

{ "sha256": "<the zip's SHA-256, in lowercase hex>", "size": <the zip's length in bytes> }
```

The API answers with one request the pipeline may make of S3:

```json
{
  "method": "PUT",
  "url": "https://<bucket>.s3.eu-west-2.amazonaws.com/<domain>/bundle/<sha256>.zip?X-Amz-...",
  "headers": {
    "if-none-match": "*",
    "x-amz-checksum-sha256": "<the zip's SHA-256, in base64>"
  },
  "expiresInSeconds": 300
}
```

The pipeline sends the zip to `url` with those headers, within five minutes. The address carries
the signature of the API's own role, so the pipeline needs no AWS credentials, and the signature
is good for that one request. It covers three headers, and S3 refuses an upload that differs in
any of them:

- **`content-length`,** the size the pipeline gave, so no other length is accepted.
- **`x-amz-checksum-sha256`,** the hash the pipeline gave. S3 checks the body against it, so
  the object under a key is the bundle the key names.
- **`if-none-match: *`,** so S3 writes only where there is no object. A bundle that is already
  there gets a 412 from S3, which a pipeline takes as done: the key is the bundle's hash, so
  what is there is the same bundle.

The key is `<domain>/bundle/<sha256>.zip`. The domain is the one the pipeline was allowed for,
so a pipeline can write only under its own domain. The API's role may write and read keys of that
shape, and list the bucket, and nothing else there. A signature carries no more than the signer's
permission, and covers its method, so no address the API signs can read or delete a bundle.

The bucket is `shared-domain-code-<account>`, in the stage's shared account, built by
`DomainCodeBucket` in `shared/infra`. Its policy refuses, from anyone:

- a write by any role but the API's. A key is the bundle's hash only because the API signs each
  upload with that checksum, so a write it didn't sign could put other code under a bundle's key
  before the bundle is uploaded, and the bundle's own upload would then get a 412;
- a write that doesn't carry `If-None-Match`;
- a request on a presigned address signed more than five minutes before, so an address lasts no
  longer than the API says even if the API signs for longer;
- any delete of an object or a version of one;
- any change to the bucket's lifecycle rules, which could expire objects without a delete.

So under that policy a key holds only the bundle it names, and a bundle, once uploaded, is
neither replaced nor removed. A released function's code stays in the bucket, so this is also
what keeps it running.

The policy grants two reads of a bundle, by version, in each domain account of an environment that
publishes:

- Lambda may read one for a domain's function. It names each account with `aws:SourceAccount` and
  its functions, `domain-<environment>-*`, with `aws:SourceArn`.
- A domain's [deploy role](#permissions) may read one, since Lambda reads the bundle a function is
  created or updated from as the caller. One statement names every such account, and its deploy
  roles, `domain-<environment>-*-deploy`, with `aws:PrincipalArn`. S3 refuses a policy that names a
  role that doesn't exist yet, and the domain stacks that create the roles deploy after this one.

Both name an account's domains by pattern, never one by one, so the policy grows with the domain
accounts and not with the domains. Each deploy role's own policy holds it to its domain's bundles.

#### Releasing a bundle

Once its bundle is uploaded, the pipeline asks for its release by the same hash:

```http
POST /ci/environments/<environment>/domains/<domain>/releases
content-type: application/json
x-flex-ci-token: <the job's token>
x-amz-content-sha256: <this body's SHA-256>

{ "sha256": "<the zip's SHA-256, in lowercase hex>" }
```

The API looks for `<domain>/bundle/<sha256>.zip`, under the domain the pipeline was allowed for,
so a pipeline can release only its own domain's code. If there is no such object, it answers
409, `No bundle with this hash has been uploaded`. Otherwise it records the release, with the
object's version, in the [release table](#the-release-table), puts its key on the
[release worker](#the-release-worker)'s queue, and answers 202 with the release's ID:

```json
{
  "releaseId": "<the release's ID>",
  "environment": "<environment>",
  "domain": "<domain>",
  "sha256": "<the zip's SHA-256>"
}
```

The release is queued, not done. Each request is a release of its own: asking again for the
bundle already on `live` publishes no new version and leaves `live` where it is. If the queue
refuses the message, the API records the release `refused`, at the step `queue`, and answers 500:
no message is behind it, so it will never be tried, and the pipeline asks again.
The pipeline can't yet ask how a release went: the worker's log and the table say.
