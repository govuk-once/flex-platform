A domain owns a feature's behaviour and the API the app uses to reach it. The platform provides
the Frontdoor, domain hosting and gateways to upstreams. The examples here show how to divide the
work between them. [Domain configuration](/flex-platform/domains/configuration/) covers how a
domain declares its routes.

## Start with the app's request

Describe what the person using the app needs to see or change. Then identify the data and
upstream operations needed to do it. A domain's API can combine these operations into one request.

| Shape | What the domain does | Example |
|---|---|---|
| One upstream call | Calls a gateway operation and presents its result through the domain's API. | Reading a user's notification preferences. |
| Several upstream calls | Resolves dependencies between calls and combines their results. | Looking up a user's notification identifier, then retrieving their notifications. |
| Local computation | Computes a response from the request and bundled reference data. | Returning a derived value without contacting an upstream. |

One domain can use several of these shapes. The feature's needs decide how many gateway calls it
makes. A gateway stays specific to one upstream.

## Two contracts

The app calls a domain's HTTP API. The domain calls a gateway using its generated
[call contract](/flex-platform/codegen/call-contract/). The domain translates between them:

- it supplies the operation's input from the authenticated request and its own business logic;
- it handles the gateway's named outcomes and error codes;
- it chooses the response the app receives.

For example, a missing linked account may mean the app should offer account linking. The domain
decides that behaviour. The gateway reports the upstream result through its declared contract.

The gateway's driver owns upstream addresses, credentials, transport headers and status mapping.
The domain combines information from different upstreams and decides what it means for a feature. A [custom gateway handler](/flex-platform/drivers/openapi-rest/handlers/)
can adapt one upstream's behaviour to its gateway contract.

## Identity and linked accounts

An authenticated app user and their record in another service may have different identifiers.
The User Data Platform holds links between service identities. A domain may need to resolve that
link before it can call the service the person wants to use. Authentication alone does not show
that the account has been linked, or that every requested record belongs to the user.

Design the domain to handle each of these separately, because each can need a different response
in the app:

- a missing link;
- a missing upstream record;
- an upstream failure.

<Aside type="caution" title="Bindings hold a call to its user, not to a service's records">
A gateway verifies the caller token and compares the fields an operation binds with its
`pairwiseId` and `service`. A field naming the user at another service is not bound, because no
claim vouches for it. A domain must still check that such an ID belongs to its caller, through the
link the User Data Platform holds. See [Secure bindings](/flex-platform/gateways/configuration/#secure-bindings).
</Aside>

## Data and dependencies

A gateway exposes specific operations with specific input and outcome schemas. A User Data
Platform gateway does not give a domain an arbitrary data store. A new stored shape or upstream
operation needs an explicit gateway contract. See
[Narrowing what the document leaves open](/flex-platform/drivers/openapi-rest/deriving-schemas/#narrowing-what-the-document-leaves-open).

Check the configured operations before designing a feature around them. The
[UDP gateway configuration](https://github.com/govuk-once/flex-platform/blob/main/gateways/services/udp/gateway.config.ts)
is the implemented example. Other upstream integrations need gateway work before a domain can
use them. This repository does not provide domain-owned storage or background execution.

## Failures across several calls

Each gateway call has its own result. A sequence of calls is not a transaction: if a later call
fails, an earlier successful write is not undone. Before combining writes behind one app request,
decide what a partial result means for the feature.

A timeout does not show whether an upstream completed a write. The gateway client sends each call
once, as described under [Calling gateways](/flex-platform/domains/overview/#calling-gateways). The
feature's design must handle partial success, and decide whether an operation can safely be
repeated.
