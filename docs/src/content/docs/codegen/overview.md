`gateway-codegen` runs in a gateway package. It loads `gateway.config.ts` and the latest version in
`schemas/`, and writes everything it generates to `.gen/`:

```bash
pnpm --filter @govuk-once/flex-gateway-udp codegen   # one gateway
pnpm codegen                                         # every gateway with a codegen script
```

There is no build step. The CLI runs from source: `bin/gateway-codegen.js` registers tsx and
imports `src/cli.ts`. This means the CLI and the configurations it loads can use all of
TypeScript, not only the subset that Node can strip on its own.

## Output

The output is split into two directories because they are deployed separately. `runtime/` is what
the gateway runs. `client/` is what a service that calls the gateway imports.

| Path | Contents |
|---|---|
| `.gen/runtime/entry.js` | The handler. It combines the configuration, the validators and the executor the driver builds. It reads the environment and exports `handler`. See [The entry point](/flex-platform/codegen/entry-point/). |
| `.gen/runtime/validators/` | Standalone Ajv validators: one for each operation's input and one for each declared outcome. Self-contained JavaScript with no package imports. |
| `.gen/runtime/bundle.mjs` | `entry.js` and everything it imports, bundled by esbuild as ESM for Node 24. Only Node's builtins are left for the platform to resolve. This is the deployed artifact, and its handler is `bundle.handler`. |
| `.gen/client/rpc.ts` | The call contract as types: each operation's input and the union of its outcomes. See [The call contract](/flex-platform/codegen/call-contract/). |

No package includes `.gen/` in its TypeScript project, so neither half is typechecked where it is
written. Nothing outside `.gen/` imports the runtime half. The validators are read by the
generated entry point, which is also in `.gen/`.

`client/rpc.ts` is different. It exists so that the service calling the gateway can import it and
typecheck it with its own sources. A codegen test also compiles a generated contract, so the
generated output is checked in at least one place.

## Order of a run

Codegen checks a gateway before it writes anything:

1. The configuration is loaded. Every schema version is read and its shape checked.
2. The latest version's schemas compile in Ajv's strict mode.
3. Each version is compared with every version before it. See
   [Compatibility](/flex-platform/gateways/compatibility/).
4. The configuration is checked against the latest version, first generically and then through the
   driver's `checkSchemas`. See [What codegen checks](/flex-platform/codegen/checks/).
5. Where the driver can derive without the network, the latest version is checked to be what it
   derives. See [What the driver derives](/flex-platform/codegen/checks/#what-the-driver-derives).
6. Then `.gen/` is deleted and written again with the validators, entry point, bundle and
   contract.

A gateway these checks reject keeps its existing output. After that point, writing and bundling
can still fail, and so can the contract, which refuses a schema it cannot express as types, such
as two names that would collide. A failure there fails the command and leaves an incomplete
`.gen/`. The next run replaces it.

## Guarantees and limits

- **Each run reads from disk.** It reads `gateway.config.ts` and the latest version in `schemas/`
  from the files on disk, not from anything a process loaded earlier. This matters because the
  entry point imports the configuration, and esbuild reads it again when it bundles.
- **One gateway is generated per process.** Node reuses a module it has already evaluated, and
  codegen cannot remove one from its cache. On a second run in the same process, whatever the
  configuration imports would be out of date. The command does one run.
- **One run at a time for each generated directory.** Nothing coordinates two runs, and a gateway
  is generated by one command.
- **The bundle is built during generation, not at deployment.** A gateway that cannot be bundled
  fails at a point where the cause is easy to find. The same gateway always bundles to the same
  bytes.

## Validators

Validators are Ajv standalone code, generated from the latest schemas. They are self-contained
JavaScript. Ajv's runtime helpers and formats are bundled into them at generation time, resolved
from codegen's own dependencies. This means:

- the validators run without codegen or Ajv installed;
- no one keeps a manual list of helpers;
- the validators have no package imports and no declaration files.

The validators read only the fields an object holds, never fields it inherits. Every value a
validator sees was parsed from JSON, so it inherits from `Object.prototype`. Without this rule, a
schema naming `constructor` or `toString` would be answered by the prototype, and an empty object
would satisfy a requirement for such a field.
