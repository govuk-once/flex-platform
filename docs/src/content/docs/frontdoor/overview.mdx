Every request from the GOV.UK app enters Flex through one CloudFront distribution, on one domain
name, whichever domain the request is for. AWS WAF protects the distribution. The code is under
`frontdoor/`, and each environment's [stacks](/flex-platform/infrastructure/overview/#stacks)
deploy it. AWS Shield Advanced and alarms are planned.

On its way in, a request passes three layers. Each turns away what it can before the next is paid
to look at it:

1. [WAF](#waf) limits body size and request rates, and applies AWS's managed rules.
2. The [CloudFront Function](/flex-platform/frontdoor/cloudfront-function/) checks the request's
   structure: its method, the token's shape, the path and the content type.
3. [Lambda@Edge](/flex-platform/frontdoor/lambda-edge/) verifies the Cognito access token, routes
   the request to its domain, and signs it.

## The distribution

The distribution answers at the apex of the frontdoor account's hosted zone, such as
`production.flex-domainedge.once.service.gov.uk`. The zone already exists, delegated, in each
frontdoor account, and [config](/flex-platform/infrastructure/overview/#config) names it. The stack
creates no zone. It writes three things into it:

- a CAA record, `0 issue "amazon.com"`, so only Amazon may issue certificates for the zone's
  names. It is written before the certificate, because ACM checks CAA before it issues;
- the validation record for an ACM certificate for the apex, in us-east-1;
- A and AAAA alias records for the apex, pointing at the distribution.

Viewers connect over HTTPS only, with TLS 1.2 or 1.3 and AES-GCM ciphers (`TLSv1.2_2025`), by
SNI, over HTTP/2 or HTTP/3. A plain HTTP request gets CloudFront's 403, never a redirect. The
distribution serves from CloudFront's edges in North America and Europe (`PriceClass_100`), and
publishes CloudFront's additional metrics, which include the 401 rate and origin latency.

It has one behaviour, for every path:

- **Every method reaches the CloudFront Function,** which refuses the ones the platform doesn't
  serve.
- **Nothing is cached** (`CachingDisabled`). See
  [where Lambda@Edge runs](/flex-platform/frontdoor/lambda-edge/#where-it-runs) for why this
  matters.
- **The default origin is an empty, private S3 bucket.** CloudFront resolves the origin's name
  before Lambda@Edge runs, and answers 502 without running it if that fails, so the origin must be
  a name that resolves, and ours. Nothing signs requests to the bucket, so a request that reached
  it would get S3's own refusal, and the caller's token would never be replaced with a signature.
  Lambda@Edge sends every request it forwards to its domain's origin instead, so nothing reaches it.
- **Lambda@Edge runs at origin request,** with the request body, which it signs.

### Response headers

A response headers policy sets these on every response, overriding whatever the origin sent, so a
domain can't weaken them:

| Header | Value |
|---|---|
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `Content-Security-Policy` | `default-src 'none'; frame-ancestors 'none'` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` |
| `Referrer-Policy` | `no-referrer` |
| `X-Permitted-Cross-Domain-Policies` | `none` |
| `Cross-Origin-Resource-Policy` | `same-origin` |
| `Cache-Control` | `no-store`, so a personal response stays out of every cache on the way |

It removes the headers Amazon API Gateway adds that name its internals: `x-amz-apigw-id`,
`x-amzn-trace-id` and API Gateway's `x-amzn-remapped-*` set. CloudFront refuses to remove
`x-amzn-requestid`, so that one reaches the caller.

## WAF

The web ACL, `frontdoor-<environment>-web-acl`, allows a request unless a rule blocks it. Its rules, in the
order WAF evaluates them:

| Rule | Action | What it does |
|---|---|---|
| `BodySizeLimit` | 413 | Blocks a body over 16 KB. A body WAF can't inspect in full counts as over. |
| `AWSManagedRulesCommonRuleSet` | The group's own | AWS's common rules. Its `SizeRestrictions_BODY` rule only counts, because its 8 KB limit would block bodies the platform accepts. |
| `AWSManagedRulesKnownBadInputsRuleSet` | The group's own | Request patterns known to be malicious. |
| `AWSManagedRulesSQLiRuleSet` | The group's own | SQL injection. |
| `AWSManagedRulesAnonymousIpList` | Count only | Matches VPNs, proxies and hosting providers. Its matches show in metrics and logs, and nobody is turned away. |
| `RateLimitPerToken` | 429 | More than 1,000 requests with one `Authorization` value in five minutes. |
| `RateLimitPerIp` | 429 | More than 5,000 requests from one address in five minutes. It is higher than the per-token limit, for networks many people share. |

WAF inspects the first 16 KB of a body, the same as the body limit, so the managed rules see the
whole of every body that gets through. The per-token limit counts the header's exact value, so
both edge functions accept a token in
[one form only](/flex-platform/frontdoor/cloudfront-function/#one-form-per-token). A request
without the header isn't counted per token, and the CloudFront Function refuses it.

The 413 and 429 have JSON bodies in the shape the app handles:
`{"message":"Request body too large","type":"client_error"}` and
`{"message":"Too many requests","type":"client_error"}`. A managed rule's block is WAF's own 403.

WAF logs every request to `aws-waf-logs-frontdoor-<environment>-web-acl`, in us-east-1. `authorization` and
`cookie` are redacted from the logs and replaced in sampled requests, so no credential reaches
either. Each rule publishes metrics under its own name.

AWS's IP reputation list isn't used. It blocks addresses AWS's threat intelligence flags, and
GitHub's hosted runners are among them, which would block the platform's own end-to-end tests.

## Logs

Every log group the Frontdoor writes to is one its stacks create, before anything writes to it.
Each keeps its logs for a year, is encrypted with its stack's KMS key, and is kept when its stack
is deleted.

| Log group | Region | Written by |
|---|---|---|
| A name CloudFormation generates | us-east-1 | CloudFront's access logs, through standard logging v2 |
| `aws-waf-logs-frontdoor-<environment>-web-acl` | us-east-1 | WAF |
| `/aws/cloudfront/function/frontdoor-<environment>-viewer-request` | us-east-1 | The CloudFront Function, from every edge |
| `/flex/frontdoor/<environment>/origin-request` | eu-west-2 | Lambda@Edge |

Lambda@Edge writes in the region each copy of the function ran in, to the group the function
names. That group exists only in eu-west-2, in a stack of its own,
`frontdoor-<environment>-edge-logs-eu-west-2`, and the role may write only there. So no copy
creates a log group anywhere else, and **lines from copies that ran outside eu-west-2 are
dropped.** The access logs and the CloudFront Function's lines still cover every request.

A writer to a log group encrypted with a customer managed key needs that key as well as the log
group. Lambda@Edge's role is granted its group's key. CloudFront writes the CloudFront Function's
lines as its service-linked role, `AWSServiceRoleForCloudFrontLogger`, whose policy is AWS's, so
the key's own policy grants that role, by ARN, for that one log group. It's matched by ARN because
KMS refuses a policy naming a role that doesn't exist yet, and CloudFront creates this one when it
first needs it.

CloudFront itself writes to `/aws/cloudfront/LambdaEdge/<distribution ID>`, in the region the
function ran, when the function returns something CloudFront refuses. The platform can't prevent
or redirect those writes, and doesn't create, retain or forward that group. Each entry holds the
request's method, path and query string, but no header, token or body. A domain's paths and query
strings must never carry personal data: they also reach the access logs and WAF's logs.
